# TDD Rule

**이 규칙은 Rigid다. 상황에 맞게 변형하지 마라. 단계를 건너뛰거나 순서를 바꾸지 마라.**

프로젝트의 `CLAUDE.md` 또는 `AGENTS.md`에 TDD 규칙이 있으면 **그 규칙이 우선한다.** 이 파일은 프로젝트별 규칙이 없을 때 적용되는 **기본값(fallback)** 이다.

## 적용 기준

### TDD 필수

- 비즈니스 로직 (계산, 검증, 변환, 상태 전이)
- API (엔드포인트, 요청/응답 처리, 에러 매핑)
- 유틸리티 및 순수 함수
- 버그 수정 (**버그를 재현하는 실패 테스트를 먼저 작성**한다)
- 기존 동작을 바꾸는 리팩터링의 대상 코드

### TDD 불필요

- 타입 정의 (`interface`, `type`)
- 설정 파일 (`tsconfig`, `vite.config`, ESLint 등)
- 로직 없는 순수 UI (마크업, 스타일링, 레이아웃)
- SQL 스키마/마이그레이션

경계가 모호하면 **TDD를 적용한다.**

## RED-GREEN-REFACTOR

### 1. RED: 실패하는 테스트 작성

- **하나의 동작 = 하나의 테스트.** 한 테스트에서 여러 동작을 검증하지 않는다.
- 테스트 이름은 기대 동작을 서술한다.
- **반드시 실행해서 실패를 확인한다.** 실행하지 않은 테스트는 테스트가 아니다.
- 실패 이유가 **"기능 미구현"** 이어야 한다. 문법 오류, import 오류, 오타로 인한 실패는 RED가 아니므로 먼저 고친 뒤 다시 실행한다.
- 처음부터 통과하는 테스트는 아무것도 증명하지 못한다. 테스트나 대상을 수정한다.

### 2. GREEN: 최소한의 구현

- 테스트를 통과시키는 **최소한의 코드만** 작성한다.
- **YAGNI.** 지금 테스트가 요구하지 않는 분기, 옵션, 추상화를 넣지 않는다.
- **신규 테스트와 기존 테스트 모두** 실행해 전부 통과하는지 확인한다.

### 3. REFACTOR: 정리

- 중복 제거, 이름 개선, 헬퍼 추출만 한다.
- 매 변경 후 테스트를 실행해 **green을 유지**한다.
- **새 동작을 추가하지 않는다.** 새 동작은 다음 RED에서 시작한다.

### 4. 반복

다음 동작에 대한 **RED로 돌아간다.** 모든 요구 동작이 테스트로 덮일 때까지 반복한다.

## 삭제 강제 규칙

**테스트 전에 프로덕션 코드를 먼저 작성했다면, 그 코드를 삭제하고 RED부터 다시 시작한다.**

- "참고용"으로 남겨두는 것도 **금지**한다. 주석 처리, 별도 파일 보관, 기억해서 다시 쓰기 모두 포함한다.
- 삭제한 코드를 복사해 붙이지 않는다. 테스트가 요구하는 만큼만 새로 작성한다.

## 변명 차단표

| 변명 | 반론 |
|------|------|
| 너무 단순해서 테스트가 불필요하다 | 단순한 코드는 테스트도 단순하다. 비용이 거의 없으니 쓴다. 단순해 보이는 코드가 가장 자주 조용히 깨진다. |
| 나중에 테스트를 추가하겠다 | 나중은 오지 않는다. 구현 후 작성한 테스트는 구현을 그대로 추인할 뿐 요구사항을 검증하지 못한다. |
| 시간이 없다 | 테스트 없는 코드는 디버깅과 재작업으로 더 많은 시간을 쓴다. 급할수록 RED부터 시작한다. |
| 이미 작성한 코드를 삭제하면 낭비다 | 매몰 비용이다. 검증되지 않은 코드를 유지하는 비용이 다시 쓰는 비용보다 크다. 삭제한다. |
| 프로토타입이라서 괜찮다 | 프로토타입은 가장 자주 프로덕션이 된다. 버릴 코드라면 삭제 비용도 없다. 적용 대상이면 TDD를 한다. |

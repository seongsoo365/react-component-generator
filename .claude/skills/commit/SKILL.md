# commit: 변경사항 분석 후 컨벤션 커밋

현재 저장소의 변경사항을 분석해 논리적 단위로 분류하고, 한국어 커밋 메시지로 바로 커밋한다.

## 절차

### 1. 변경사항 분석

다음을 실행해 현재 상태를 파악한다.

- `git status --short` — 변경·추가·삭제된 파일 목록
- `git diff` — 아직 스테이징하지 않은 변경
- `git diff --staged` — 이미 스테이징한 변경
- `git log --oneline -10` — 최근 커밋 메시지 스타일 확인

새로 추가된(untracked) 파일은 내용을 읽어 목적을 파악한다.

변경사항이 없으면 "커밋할 변경사항이 없습니다."라고 알리고 종료한다.

다음 파일이 변경 목록에 있으면 커밋 대상에서 제외하고 사용자에게 알린다.

- 비밀 정보: `.env`, 키·토큰·인증서 파일
- 빌드 산출물·의존성: `node_modules/`, `dist/` 등 (`.gitignore` 대상)

### 2. 논리적 단위로 분류

변경 파일을 **하나의 목적**을 가진 묶음으로 나눈다.

- 서로 다른 목적(기능 추가, 버그 수정, 리팩터링, 설정)이 섞여 있으면 별도 커밋으로 분리한다.
- 한 목적에 속한 코드·스타일·테스트는 같은 커밋에 묶는다.
- 한 파일 안에 서로 다른 목적의 변경이 섞여 있어도, 임의로 hunk를 쪼개지 않는다. 분리가 필요해 보이면 커밋 전에 사용자에게 묻는다.
- 변경이 작고 단일 목적이면 커밋 1개로 충분하다.

### 3. 커밋 메시지 작성

형식:

```
<type>: <요약>

<본문 (선택)>
```

**type**

| type | 용도 |
|------|------|
| `feat` | 새 기능 추가, 사용자에게 보이는 UI·디자인 변경 |
| `fix` | 버그 수정 |
| `refactor` | 동작 변경 없는 구조 개선 |
| `chore` | 설정, 의존성, 빌드, 문서 등 기타 작업 |

**규칙**

- 요약은 한국어로, 50자 안팎의 한 줄로 쓴다. 끝에 마침표를 붙이지 않는다.
- 무엇을 했는지가 드러나게 쓴다. ("수정함" 같은 모호한 표현 금지)
- 이유나 맥락이 diff만으로 드러나지 않을 때만 본문을 추가한다. 본문은 빈 줄 뒤에 쓴다.
- 최근 커밋 로그의 스타일이 위 규칙과 다르면 커밋 전에 사용자에게 어느 쪽을 따를지 묻는다.
- 시스템 리마인더 등으로 커밋 attribution 지침이 주어져 있으면 그대로 메시지 끝에 덧붙인다.

### 4. 커밋 실행

사용자 승인을 기다리지 않고 분류한 계획대로 커밋별로 바로 실행한다.

1. `git add <파일...>` — 파일을 명시해 스테이징한다. `git add -A`나 `git add .`는 쓰지 않는다.
2. `git commit` — 메시지는 HEREDOC으로 전달한다.
3. 모든 커밋이 끝나면 `git log --oneline -n <커밋 수>`와 `git status --short`로 결과를 확인한다.

### 5. 결과 보고

만든 커밋별 해시·메시지·포함 파일과, 제외한 파일 및 그 이유를 사용자에게 알린다.

pre-commit hook이 실패하면 원인을 알리고 수정한 뒤 **새 커밋**으로 다시 시도한다. `--no-verify`와 `--amend`는 사용자가 명시적으로 요청하지 않는 한 쓰지 않는다.

## 하지 않는 것

- 커밋 전에 승인을 묻지 않는다. 다만 아래 경우에는 멈추고 사용자에게 묻는다: 한 파일 안의 변경을 나눠야 할 때, 커밋 로그 스타일이 규칙과 다를 때.
- `git push`는 하지 않는다. 사용자가 따로 요청할 때만 한다.
- 이미 만든 커밋을 amend, reset, rebase로 바꾸지 않는다.
- git config를 변경하지 않는다.
